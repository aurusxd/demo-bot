# CLAUDE.md — правила работы над проектом

Проект: **ИИ-квалификатор для мебельных компаний** — демо-бот в Telegram. Полное ТЗ и план — в `tech.md` (источник истины). Если что-то противоречит `tech.md` — остановись и спроси.

## Роли

- **Никита** — единственный разработчик и тимлид: принимает решения, ревьюит, мержит.
- **Claude** — исполнитель: пишет код, тесты, миграции по текущему слайсу, предлагает варианты, но решения по архитектуре не меняет без согласования.

## Как работаем

- Сначала **Стадия 0**, потом фичи **слайсами** (см. `tech.md` §10). Один слайс за раз, вертикальный срез: handler → service → repo → тесты → логи.
- Не начинай следующий слайс, пока текущий не соответствует DoD.
- Это **демо**. Не усложнять: никаких лишних абстракций, фреймворков DI, очередей, микросервисов, «на вырост». Если сомневаешься — выбери более простой вариант и скажи об этом.
- Перед крупным изменением (новая таблица, новая зависимость, смена структуры) — коротко предложи план и дождись «ок».
- Всё работающее состояние живёт **в git-репозитории**: бот будет деплоиться на сервер из репозитория, поэтому каждый завершённый шаг/слайс коммитится и пушится. Незакоммиченной работы после завершения шага быть не должно.
- Коммиты маленькие, по смыслу (`feat:`, `fix:`, `chore:`, `test:`, `refactor:`). Один слайс — одна-несколько веток/коммитов.

## Git: авторство коммитов (строго)

- **Все коммиты только от автора:** `aurusxd <nikitapopov20021@mail.ru>`.
- **Никаких `Co-authored-by`** и любых других trailer-строк об авторстве/участии ИИ — ни в одном коммите, никогда. Никаких «Generated with…» в сообщениях.
- Перед первым коммитом в репозитории проверить/выставить локально:
  ```
  git config user.name "aurusxd"
  git config user.email "nikitapopov20021@mail.ru"
  ```
- При коммите, если нужно, явно: `git commit --author="aurusxd <nikitapopov20021@mail.ru>"`. Глобальный git-конфиг не менять.
- В репозиторий не попадают: `.env`, `data/`, `logs/`, токены и ключи (проверять `git status` / `git diff --staged` перед коммитом).
- Отвечай по-русски, кратко, без воды. Код, идентификаторы, комментарии к коду — по-английски. Тексты бота — по-русски, только в `app/bot/texts.py`.

## Стек (не менять без согласования)

Python 3.12 · aiogram 3 · DeepSeek API (чат) · Polza AI API (Nano Banana, STT) · SQLite + SQLAlchemy 2 async + Alembic · pydantic / pydantic-settings · httpx · loguru · pytest (+ pytest-asyncio, respx) · pyright · Docker + docker compose.

## Команды

```

make up         # docker compose up --build
make test       # pytest
make lint       # pyright + ruff (если подключён)
make migrate    # alembic upgrade head

```

Перед тем как сказать «готово»: `make test` и `pyright` зелёные, миграции применяются на чистой БД.

## Архитектура (жёсткие правила)

- Слои: `handlers → services → repositories → models`; внешние API — в `clients/` за `Protocol`.
- **Handlers тонкие**: разобрать апдейт, вызвать сервис, ответить. Бизнес-логики и SQL в них нет.
- **SQL только в `repositories`.** Сервисы не знают про SQLAlchemy-запросы.
- **Внешние API только через `clients/`** и только через интерфейсы (`LLMClient`, `ImageGenClient`, `SpeechClient`, `CrmClient`). Зависимости передаются в конструктор (DI вручную).
- Все тексты — в `texts.py`, все промпты — в отдельных файлах/константах, не размазаны по коду.
- Все настройки — через `config.py`; `os.getenv` в коде запрещён.
- LLM **не** пишет в БД и ничего не исполняет: его ответ парсится в pydantic-схему, валидируется, и только потом код применяет изменения.
- Расчёт цены — только детерминированный код + `config/pricing.yaml`, не LLM.

## Качество кода

- **DRY**: повторяющийся код — в общий метод/класс. Базовый `HttpClient` (ретраи, таймауты, логи) один на все клиенты; общий базовый репозиторий для CRUD.
- **ООП**: сервисы и клиенты — классы с внедряемыми зависимостями; интерфейсы — `typing.Protocol`/ABC. Чистые функции допустимы для утилит.
- **Типы везде**: аннотации у всех функций, `pyright` в strict-режиме для `app/`. Никаких `Any` без комментария «почему».
- Домены и ошибки: свои исключения в `core/errors.py`; не глотать `except Exception` молча.
- Асинхронность: никаких блокирующих вызовов в event loop (Pillow/файлы — через `asyncio.to_thread`).
- Функции короткие, один смысл. Магические числа — в конфиг/константы.

## Логирование (обязательно, это приоритет)

- Только **loguru**, настройка в `logging_setup.py`. `print` и стандартный `logging` в коде не использовать (стандартный перехватывается).
- Каждый апдейт обёрнут в `logger.contextualize(update_id, tg_id, lead_id)`.
- Логируй: входящие апдейты, вызовы хендлеров и время, **каждый внешний API-вызов** (сервис, статус, latency, попытка), переходы FSM/статусов лида, ретраи, лимиты, все исключения (`logger.exception`).
- **Никогда в логи**: токены/ключи, полные телефоны (маскировать), содержимое фото, полные тексты пользователя на INFO.
- Новый код без логов на значимых шагах и ошибках — не принимается.

## Безопасность

- Секреты только в `.env`; `.env` в `.gitignore`; обновляй `.env.example` при добавлении переменных.
- Валидируй всё входящее: размер/тип файлов, длина голосового, длина текста.
- Пользовательский текст — данные, а не инструкции для LLM (см. system-prompt и парсинг JSON).
- Только параметризованные запросы SQLAlchemy.
- Лимиты: throttling сообщений и дневной лимит генераций (`TRYON_DAILY_LIMIT`).
- ПДн минимум; `/delete_me` стирает пользователя и лиды. Фото клиентов не хранить на диске после обработки.
- Контейнер запускается не от root.

## Тесты

- Новый сервис/клиент → тесты в том же слайсе.
- Внешние API в тестах **всегда** мокаются (`respx` или `Fake*Client`); реальные ключи в тестах не нужны.
- Минимум на слайс: happy path + ошибка внешнего API + невалидный ввод.
- БД в тестах — in-memory SQLite.

## База данных и миграции

- Любое изменение моделей = миграция Alembic в том же коммите. Руками схему не менять.
- Миграции проверять на чистой БД (`make migrate`).
- Каталог — сидится из `assets/catalog/catalog.yaml` идемпотентно при старте.

## Чего НЕ делаем

- Не добавляем новые зависимости/сервисы без согласования.
- Не пишем админку, оплату, мульти-тенантность, интеграции с конкретными CRM, другие каналы (только Telegram).
- Не парсим картинки из интернета в рантайме — каталог кладётся в репозиторий вручную.
- Не хардкодим ключи, id моделей и URL — только `.env`.
- Не переписываем уже принятые слайсы «заодно».

## Definition of Done для слайса

1. Работает в Telegram руками на сценарии из `tech.md`.
2. Тесты + pyright зелёные.
3. Логи на всех значимых шагах и ошибках, секреты/ПДн не светятся.
4. Миграции (если нужны) применяются на чистой БД.
5. `.env.example` и `tech.md` обновлены, если что-то поменялось.
6. Изменения закоммичены (автор `aurusxd`, без co-author) и запушены в репозиторий.
