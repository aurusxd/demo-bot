# tech.md — ИИ-квалификатор для мебельных компаний (демо-бот)

> Telegram-бот-демо для показа клиентам. Принимает заявки на кухни, шкафы, гардеробные, понимает текст/фото/голос, делает предварительный расчёт, отдаёт «тёплый» лид в CRM и умеет «примерить» мебель/интерьер на фото клиента.
> Принцип: **демо, а не прод**. Простота важнее полноты. Всё, чего нет в этом файле, не делаем.

---

## 1. Цели и границы

**Цель:** за 2–3 минуты показать клиенту (мебельной компании) полный путь: заявка → квалификация → расчёт → лид в CRM + вау-фича «примерить у себя».

**Входит:**
- Диалоговая квалификация заявки (DeepSeek).
- Приём текста и голосовых; фото клиента принимаются и прикладываются к лиду **без анализа** (vision нет).
- Предварительный расчёт (детерминированный, в коде).
- Передача лида: карточка менеджеру в Telegram + CRM-адаптер (в демо — заглушка/webhook).
- Каталог интерьера/мебели (фото) + «Попробовать у себя» (Nano Banana через Polza AI).
- Шапка бота (description + картинка) как на референсе.

**Не входит (сознательно):** мульти-тенантность, админ-панель, оплата, WhatsApp/ВК/Авито/MAX-каналы (только заявлено в шапке, реализуем один Telegram), реальные интеграции с конкретной CRM, горизонтальное масштабирование.

## 3. Архитектура

Слои, зависимость только сверху вниз:

```
handlers (aiogram)  →  services  →  repositories  →  models (SQLAlchemy)
                          ↓
                       clients (DeepSeek, Polza, CRM)  — за Protocol-интерфейсами
```

- **handlers** — только разбор апдейта, вызов сервиса, ответ. Никакой бизнес-логики.
- **services** — бизнес-логика (квалификация, расчёт, каталог, примерка, медиа).
- **repositories** — единственное место с SQL/SQLAlchemy-запросами.
- **clients** — внешние API. Каждый реализует `Protocol` (`LLMClient`, `ImageGenClient`, `SpeechClient`, `CrmClient`), в сервисы приходят через DI → легко мокать в тестах.
- **DI**: ручной (контейнер в `main.py`), зависимости прокидываются в aiogram через `dp.workflow_data` / middleware. Без DI-фреймворков.

## 4. Модель данных (SQLite)

Минимум таблиц.

- `users` — `id`, `tg_id` (unique), `username`, `created_at`, `tryon_used_today`, `tryon_reset_date`
- `leads` — `id`, `user_id`, `status` (`draft|qualified|sent`), `name`, `furniture_type` (`kitchen|wardrobe|walk_in`), `dimensions`, `length_m`, `price_class` (`economy|standard|premium`), `style`, `budget`, `city`, `deadline`, `phone`, `comment`, `business_role`, `lead_sources` (B2B: кто посетитель и откуда у него заявки), `estimate_min`, `estimate_max`, `created_at`, `sent_at` (CRM приняла), `manager_notified_at` (карточка ушла менеджеру)
- `messages` — `id`, `lead_id`, `role` (`user|assistant`), `content`, `kind` (`text|voice|photo`), `created_at` — история для LLM (хранить последние N)
- `lead_media` — `id`, `lead_id`, `tg_file_id`, `kind`
- `catalog_items` — `id`, `category` (`kitchen|wardrobe|walk_in|interior`), `title`, `style`, `image_path` (unique, относительно папки каталога — ключ сида), `tg_file_id` (кэш после первой отправки), `source_url`
- `tryon_requests` — `id`, `user_id`, `catalog_item_id`, `status` (`pending|done|failed`), `latency_ms`, `error`, `created_at`

Результаты генерации и фото клиентов **не храним на диске дольше обработки** (удаляем temp-файлы; в БД только `tg_file_id`).

## 5. Ключевые решения по фичам

### 5.1 Шапка бота (то, что видно до `/start`)
- Текст — Bot API `setMyDescription` (**≤ 512 символов**), кнопка «What can this bot do?» показывает его. Короткое — `setMyShortDescription` (≤ 120).
- Картинка «Менеджер или бот?» — загружается вручную через @BotFather (`/setdescriptionpic`), в API не настраивается. Файл лежит в `assets/header/`.
- Текст шапки живёт в `texts.py`; скрипт `scripts/set_bot_profile.py` (`make profile`) выставляет description, short description и список команд через API. Тест проверяет лимиты 512/120 (в UTF-16, как считает Telegram).
- **Кнопочного меню нет** — бот общается как живой менеджер. `/start` шлёт приветствие (что это демо, кратко функции бота, что подключается к любому мессенджеру или сайту, и предложение написать запрос; имя LLM спрашивает в первом ответе), снимает старую reply-клавиатуру и начинает новый черновик лида.
- Команды бота (выставляет `make profile`): `/start` и `/delete_me` (§7).
- Пользователь регистрируется `UserMiddleware` на каждом апдейте (атомарный upsert по `tg_id`), в хендлеры приходит как `user`.

### 5.2 Квалификация (DeepSeek)
- Бот ведёт диалог как живой менеджер (без кнопок) и собирает **слоты**: имя, тип мебели, размеры/план, стиль, бюджет, город, сроки, телефон.
- Сценарий: имя → коротко про бизнес посетителя (роль в мебельной компании, откуда заявки — слоты `business_role`, `lead_sources`, не настаивать) → «представьте, что вы клиент» → квалификация заказа. Если посетитель сразу пишет запрос на мебель — сразу квалификация.
- Мусор, оскорбления, офтоп: без морали и без поддержки темы, возврат к демо фразой «{имя}, я здесь, чтобы помочь вам протестировать, как ИИ может работать с клиентами. Если хотите, можем продолжить демонстрацию.» На вопрос «зачем это» — объяснить, что это демонстрация.
- Каждый ход: в DeepSeek уходит system-prompt + история (последние ~12 сообщений) + текущие слоты. Ответ — **строго JSON** (`response_format: json_object`), валидируется pydantic-схемой `LLMReply {reply: str, slots: LeadSlotsPatch, ready: bool, catalog: CatalogCategory | null}` (`catalog` — §5.6).
- При невалидном JSON — 1 ретрай с подсказкой, затем fallback-ответ «уточните, пожалуйста…». Бот не падает.
- Слоты мержатся в `leads` кодом, **LLM не пишет в БД напрямую**.
- **Короткие транзакции:** перед вызовом LLM (и любого внешнего API) сервис делает `UnitOfWork.commit()` — иначе SQLite держит блокировку записи всё время ожидания и апдейты других пользователей падают с `database is locked`. Upsert пользователя коммитится сразу.
- Апдейты одного пользователя обрабатываются строго по очереди (`UserLockMiddleware`, in-process lock — бот в одном процессе); разные пользователи — параллельно.
- Бюджет на ход LLM — 45 с на все попытки (`LLM_TURN_BUDGET_S`); DeepSeek: таймаут 30 с, 1 HTTP-ретрай. По истечении — fallback-ответ.
- Лид переходит в `qualified`, только если LLM вернул `ready = true` **и** код подтвердил, что заполнены обязательные слоты (тип, размеры, телефон) → переход к расчёту. Телефон нормализуется кодом (`+7XXXXXXXXXX`), невалидный отбрасывается; `null` в слотах не стирает уже известные значения.
- Любой свободный текст (не команда) — ход диалога: продолжает **последний лид в любом статусе** (после квалификации бот помнит имя и контекст), новый лид — только по `/start` или если лидов ещё нет. Переход `draft → qualified` происходит один раз.
- После квалификации LLM сам благодарит и пересказывает заявку; отдельной «сводки» в чат нет (структурированная карточка — менеджеру, слайс 4).
- Прошлые ответы ассистента уходят в историю в полном JSON-виде ответа (`reply` + все `slots: null` + `ready: false`), известные слоты — отдельным system-сообщением. Замеры на DeepSeek: обычный текст в истории → пустой ответ в 6/14 вызовов; только `{"reply"}` → модель перестаёт возвращать `slots`; полный формат → 0/12 пустых, слоты заполняются.
- Лимит текста пользователя — 1000 символов; ответы LLM отправляются без parse_mode (не HTML).
- Текст пользователя — это данные, а не инструкции: в system-prompt явный запрет менять роль/формат; ответ LLM не исполняется, только парсится.

### 5.3 Расчёт
- **Детерминированный, без LLM.** `config/pricing.yaml` (путь — `PRICING_PATH`, валидируется pydantic при старте): базовая цена за погонный метр по типу мебели × коэффициент класса материалов (`economy 0.8 / standard 1.0 / premium 1.4`, по умолчанию `standard`).
- LLM только **извлекает числа** в слоты `length_m` (погонные метры: кухня — сумма сторон, шкаф/гардеробная — ширина; код принимает 0,5–20 м) и `price_class` (`economy|standard|premium`); цену считает `EstimateService`.
- Результат — вилка ±15 %, округление до 1 000 ₽, сохраняется в `leads.estimate_min/max`; клиенту — отдельным сообщением после благодарности LLM, с дисклеймером «ориентир, точную стоимость назовёт менеджер после замера».
- Если длины нет (клиент не знает размеров) — расчёт не делаем: клиенту «точную стоимость посчитает менеджер после замера», лид всё равно передаётся.

### 5.4 Фото и голос
- **Голос:** длительность ≤ 60 с проверяется до скачивания → `.ogg` скачивается в память → транскрипция через Polza `POST /v1/audio/transcriptions` (JSON, `file` = base64 data-URL, `language=ru`, модель `POLZA_STT_MODEL`, провайдер `POLZA_STT_PROVIDER` → `provider.only`; таймаут 30 с, 1 ретрай) → текст идёт в тот же пайплайн квалификации (`messages.kind = voice`). Пустая расшифровка → просьба повторить; ошибка STT → просьба написать текстом.
- **Фото:** без анализа. Принимаем только сжатое фото (Telegram сам перекодирует его и убирает EXIF); картинку, присланную файлом, просим отправить как фото. Валидация: ≤ 10 МБ, скачивание в память, Pillow `verify` в `asyncio.to_thread`, формат `JPEG/PNG/WEBP`; байты сразу выбрасываются. В лид сохраняется `tg_file_id` (`lead_media`), в историю — маркер «[Клиент прислал фото]» (LLM знает, что фото есть, но его не видит). Без подписи — короткое подтверждение без вызова LLM (альбом — одно подтверждение); подпись — обычный ход диалога. Менеджеру фото пересылается вместе с карточкой лида (слайс 4). Для примерки (§5.7) фото дополнительно ресайзится ≤ 1536 px.

### 5.5 Передача лида
- На ходе перехода `draft → qualified`: ответ LLM → вилка клиенту → карточка каталога (если LLM её запросил) → `LeadService.submit` (медленная доставка — после всех ответов клиенту).
- `LeadService.submit` → `CrmClient.send(LeadPayload)` + карточка в чат менеджера (`ADMIN_CHAT_ID`, обязателен) через `LeadNotifier`: HTML, все значения экранированы, полный телефон, вилка; фото лида следом (1 — фото, 2–10 — альбом).
- Доставка отмечается двумя независимыми метками: `status = sent` + `sent_at` (CRM приняла) и `manager_notified_at` (карточка ушла). `submit` делает только недостающее, поэтому повтор безопасен: карточка не дублируется, CRM не получает лид дважды. Ошибки CRM/Telegram логируются, клиент их не видит.
- **Повтор доставки** (`LeadDeliveryRetrier`): при старте и каждые `LEAD_RETRY_INTERVAL_S` (300 с) — лиды `qualified` (CRM не приняла, бот упал между квалификацией и отправкой) и `sent` без карточки. Каждый лид обрабатывается под той же per-user блокировкой (`UserLocks`), что и апдейты пользователя, — гонки с хендлером нет. Лимита попыток нет (демо): при постоянной ошибке CRM повторы идут бесконечно, каждая — в лог.
- **Дополнения после доставки**: диалог продолжается на том же лиде. Если менеджеру карточка уже ушла, то изменённые слоты — короткой карточкой «✏️ Дополнение к заявке #N» (только изменённые поля; при смене типа/длины/класса — пересчитанная вилка), новое фото — фото с подписью «📎 Дополнение к заявке #N». В CRM — полный лид с `event = lead.updated` (только если CRM уже приняла лид; иначе свежие данные уйдут с повтором). До доставки ничего не досылается: первая карточка содержит всё. Неудачное дополнение логируется и не повторяется.
- Тело для CRM — `LeadPayload` с полем `event`: `lead.created` | `lead.updated`; `lead_id` позволяет CRM отсечь дубли при ретрае POST.
- Демо: `LogCrmClient` (в лог — только id и названия заполненных полей) и `WebhookCrmClient` (POST JSON на `CRM_WEBHOOK_URL`, таймаут 15 с, 1 ретрай; URL считается секретом и маскируется в логах). Реальные CRM клиент подключит позже — через тот же `Protocol`.

### 5.6 Каталог
- Источник: `assets/catalog/catalog.yaml` (путь — `CATALOG_PATH`) + файлы фото рядом (`image` — относительный путь). При старте yaml валидируется pydantic (`CatalogConfig`: категория, заголовок, путь без `..`, jpg/png/webp, без дублей) и проверяется, что все файлы есть, — иначе бот не стартует.
- Сид при старте идемпотентный, ключ — `image_path`: новые позиции добавляются, у существующих обновляются поля (кэш `tg_file_id` сохраняется), исчезнувшие из yaml удаляются. Порядок карточек — порядок добавления (`id`). Чтобы заменить фото — новое имя файла (кэш привязан к пути).
- Фото берём из интернета **вручную** и кладём в репозиторий (не парсим на лету). Сейчас — 24 фото с Unsplash (бесплатная лицензия), по 6 на категорию, перекодированы ≤ 1280 px без метаданных; в `source_url` — страница фото. ⚠️ Это демо — для боевого использования заменить на фото клиента/лицензионные.
- **Вход из диалога**: в `LLMReply` поле `catalog` (`kitchen|wardrobe|walk_in|interior|null`, неизвестное значение → `null`). LLM ставит его, когда клиент просит показать примеры или соглашается на предложение (промпт: предложить один раз, когда понятен тип мебели). Код после ответа LLM шлёт первую карточку категории. Постоянного меню и команды нет.
- **Карточка**: фото + подпись (название, стиль; HTML, значения экранируются). Inline-кнопки только под карточкой: `◀ n / N ▶` (если позиций > 1, листание по кругу) и переключатель категорий 2×2 (текущая — неактивная). Нажатия редактируют ту же карточку (`editMessageMedia`), чат не засоряется; `callback_data` = `cat:<category>:<index>`, индекс от клиента приводится по модулю.
- **Кэш `file_id`**: первая отправка — файл с диска, `file_id` из ответа Telegram сохраняется в `catalog_items.tg_file_id`; дальше — по `file_id`. Если Telegram отверг `file_id` (сменили токен бота) — перезалив с диска и новый кэш. «message is not modified» (двойное нажатие) игнорируется. Ошибка Telegram на нажатии — alert «Что-то пошло не так». Сбой карточки в ходе диалога (Telegram или чтение файла) не пробрасывается: логируется, клиенту — «не получилось загрузить примеры», а доставка лида / дополнение на этом ходе всё равно выполняются.
- Под карточкой — кнопка «🏠 Попробовать у себя» (§5.7), `callback_data` = `try:<item_id>`.
- Объём для демо: ~5–8 позиций на категорию.

### 5.7 «Попробовать у себя» (главная вау-фича)
1. Пользователь листает каталог → жмёт «🏠 Попробовать у себя» под карточкой. Код проверяет, что позиция есть (id из `callback_data` — от клиента) и не исчерпан дневной лимит (иначе alert), и просит фото комнаты: FSM-состояние `TryOn.waiting_photo` (`MemoryStorage`, в `data` — `item_id`; рестарт бота сбрасывает ожидание — для демо ок).
2. Фото в этом состоянии — не фото к лиду. Из альбома берётся только первое фото: остальные фото этого альбома пропускаются (одна платная генерация на альбом, к лиду не прикладываются). Валидация как в §5.4 (≤ 10 МБ, Pillow `verify`), ресайз ≤ 1536 px в JPEG (EXIF-поворот применяется, метаданные выкидываются), всё в памяти. Референс из каталога так же нормализуется в JPEG.
3. Любое другое сообщение в ожидании фото (текст, голос, `/start`…) снимает состояние и обрабатывается как обычно — клиент передумал. Если генерация не удалась, состояние остаётся: можно прислать фото ещё раз.
4. `TryOnService.generate` → `ImageGenClient.edit(room, reference, prompt)` — Nano Banana через Polza `POST /v1/media` (модель `POLZA_IMAGE_MODEL`, провайдер `POLZA_IMAGE_PROVIDER` → `provider.only`). Промпты — `app/prompts/tryon.py`: для мебели «впиши эту мебель в комнату», для категории `interior` — «оформи комнату в стиле референса»; в обоих — сохранить стены, окна, перспективу и свет.
5. Пока идёт генерация — сообщение «⏳ Генерирую…» (удаляется после) + chat action `upload_photo`. Результат — фото с подписью «визуализация ИИ, точный проект — после замера» и кнопками «🔄 Другая мебель» (новая карточка той же категории, результат остаётся в чате) и «📝 Оставить заявку» (ход диалога с текстом «Хочу оставить заявку. На примерке у себя понравился вариант «…»» — LLM продолжает квалификацию; кнопки снимаются, чтобы не дёргать LLM повторно).
6. Таймауты: HTTP 90 с и 1 ретрай, общий бюджет генерации 120 с (`TRYON_BUDGET_S`: чтение референса + API + опрос + скачивание). Генерация платная и не идемпотентная: `POST /media` повторяется (`HttpClient(idempotent=False)`) только если запрос точно не начал выполняться — ошибка соединения, 429, 503; после таймаута чтения и 500/502/504 генерация может ещё идти, повтор заплатил бы дважды. Результат с CDN проверяется до отправки: ≤ 10 МБ (лимит Telegram), Pillow `verify`, JPEG/PNG/WEBP — иначе попытка `failed` и лимит не тратится. Ошибка/таймаут → «Не получилось сгенерировать, пришлите фото ещё раз».
7. Каждая попытка — строка в `tryon_requests` (`pending` → `done|failed`, `latency_ms`, короткая `error` без содержимого). Коммит до вызова API (SQLite не держит блокировку).
8. **Лимит**: `TRYON_DAILY_LIMIT` (5) генераций на пользователя в сутки (UTC) — `users.tryon_used_today` + `tryon_reset_date`. Неудачная генерация лимит не тратит. Пользователи из `ADMIN_IDS` без лимита (показ демо клиентам).
9. Фото комнаты и результат на диск и в БД не попадают; комната к лиду не прикладывается. Ссылка на результат на CDN Polza (живёт 7 дней) — это доступ к фото клиента, в логи не пишется (`HttpClient(log_path=…)`); CDN качается отдельным клиентом без API-ключа.

## 6. Логирование (loguru) — обязательно

- Единая настройка в `logging_setup.py`: stdout (человекочитаемо) + файл `logs/app.log` (JSON, `serialize=True`, rotation 10 MB, retention 14 дней, compression).
- Перехват стандартного `logging` (aiogram, httpx, sqlalchemy) в loguru.
- **Контекст**: `logger.contextualize(update_id=..., tg_id=..., lead_id=...)` в middleware на каждый апдейт — каждая строка лога привязана к пользователю/апдейту.
- **Что логируем:**
  - входящий апдейт (тип, user, длина текста — не весь текст), хендлер, время обработки;
  - каждый вызов внешнего API: сервис, метод, статус, latency, номер попытки, размер payload (не содержимое);
  - переходы FSM и статусов лида;
  - лимиты/ошибки валидации/ретраи;
  - необработанные исключения — `logger.exception` + глобальный error-handler aiogram.
- **Чего не логируем:** токены/ключи (фильтр-маскирование в sink), телефоны (маска `+7***1234`), содержимое фото, полные тексты сообщений на уровне INFO (только DEBUG и только локально).
- Уровень — `LOG_LEVEL` из `.env`.

## 7. Безопасность (минимально достаточная для публичного демо)

- Секреты только в `.env` / env-переменных, `.env` в `.gitignore`, `.env.example` в репозитории. Токены не попадают в логи.
- Все настройки — через `pydantic-settings`, при старте валидация (бот не стартует без обязательных).
- Входные данные: лимит размера файла (≤ 10 МБ), whitelist MIME (`jpeg/png/webp`), проверка через Pillow, голосовые ≤ 60 с.
- Throttling-middleware (скользящее окно): не более `THROTTLE_MAX_MESSAGES` апдейтов за `THROTTLE_WINDOW_S` на пользователя (по умолчанию 10/60 с). Лишние отбрасываются до БД и LLM; предупреждение — один раз на всплеск. Нажатия кнопок (листание каталога, LLM не вызывают) считаются отдельно — `THROTTLE_MAX_CALLBACKS` (60) за то же окно — и не съедают лимит диалога; отброшенное нажатие всегда получает ответ «вы пишете очень быстро», чтобы кнопка не зависала.
- Лимит дневных генераций (см. 5.7).
- Prompt-injection: см. 5.2 — вывод LLM только парсится и валидируется схемой.
- SQL — только через SQLAlchemy (параметризация), никакого сырого SQL со строками пользователя. Движок создаётся с `hide_parameters=True`: параметры запросов (тексты, телефоны) не попадают в исключения и логи.
- Docker: непривилегированный пользователь, `read_only` rootfs где возможно, volume только для `data/` и `logs/`.
- ПДн (телефон): храним минимум, команда `/delete_me` сразу (без подтверждения) стирает пользователя, его лиды, историю, фото лидов и примерки (`ON DELETE CASCADE`) и сбрасывает FSM-состояние (ожидание фото для примерки). Карточки, уже ушедшие менеджерам, и лиды, принятые CRM, живут вне бота и не удаляются. Следующее сообщение — новый пользователь с чистого листа.
- Админ-функции (если появятся) — только для `ADMIN_IDS`.

## 9. Открытые вопросы / риски

1. ~~**DeepSeek не умеет аудио**~~ → решено (слайс 3): STT через Polza `POST /v1/audio/transcriptions`, модель `openai/whisper-1`, провайдер `openai`. Через Media API (`/v1/media`) STT не работает — по доке вернёт `RESULT_EXPIRED`.
2. ~~**Nano Banana через Polza**~~ → решено (слайс 6), проверено реальным вызовом: `POST /v1/media`, `input.images = [{type: "base64", data: "data:image/jpeg;base64,…"}]` (комната, референс), `output_format: jpeg`. Без `async` запрос ждёт ~30 с и сразу отвечает `completed` с `data: [{url}]` (стоимость ~3 ₽); на `pending`/`processing` клиент опрашивает `GET /v1/media/{id}` раз в 3 с. Результат скачивается по URL с CDN.
3. **Качество примерки** зависит от промпта и референса — заложить время на итерации промпта (в `texts.py`/`prompts/`, не в коде).
4. **Авторские права на фото каталога** — для демо ок, для клиентского показа заменить.
5. SQLite + async: один процесс бота, этого достаточно; при росте — смена `DATABASE_URL` на Postgres без переписывания (SQLAlchemy).
